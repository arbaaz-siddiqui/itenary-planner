# Plan: all countries, admin panel, OpenTelemetry

Branch `feat/global-admin-otel` (from `release/2026.10`). Three parts, each on its own
sub-branch merged here with `--no-ff`: `feat/all-countries`, `feat/admin-panel`,
`feat/otel-observability`. Nothing goes to a deployment branch until the user says so.

Decisions (user, 17 Nov 2026): admins are the accounts listed in `ADMIN_EMAILS`;
telemetry goes to any OTLP backend set by env, off when unset; the admin panel lives in
the web app at `/admin` and shows users and activity, searches, full chat transcripts and
usage dashboards.

---

## 1. All countries (`feat/all-countries`)

Today the only real gate is `reference_data/cities.json`: Dubai is the only city with a
supplier `city_id`, so every other destination fails `resolve_city(...).city_id`, and each
tool adds "Dubai only" wording. The supplier sells worldwide: its public autocomplete
(`call_entity_search`) resolves London, Bangkok, Paris, Bali with `cityId`/`countryId`, and
a Singapore tour search returned 575 priced tours.

1. **City resolution.** `resolve_city` keeps `cities.json` first (curated, fast), then falls
   back to the supplier: `call_entity_search` city rows (and `call_hotel_cities` when needed)
   for `city_id`, `country_id`, `country_name`, lat/lng. Cached per process. Ordinary words
   must still not resolve as cities (existing tests).
2. **Flights.** Any destination needs an IATA code: accept a 3-letter code directly, and add
   `reference_data/airports.json` (city -> main IATA airports, name, lat/lng), generated by a
   script from public airport data (large and medium airports with scheduled service).
3. **Hotels.** Already take any `city_id`. Area filter: Dubai keeps `dubai_areas.json`; other
   cities match the area against the hotel's address text. No "Dubai" fallbacks.
4. **Tours, restaurants, packages.** Remove "Dubai only / offer the Dubai equivalent";
   unsupported now means "the supplier has nothing for that city". Fix the packages
   `int(None)` crash for cities without an id.
5. **Transfers.** `search_airport_transfer_dubai` becomes `search_airport_transfer`
   (destination city + hotel); the airport comes from `airports.json` for that city, not
   `default_dubai_airport`. Prompts, agent regex, cache map, Streamlit and tests updated.
6. **Visa.** Destination country resolved from the supplier's own visa country list
   (`call_visa_countries`); a country the supplier does not sell gets a clear "not
   available" answer. Weekend and "UAE immigration" wording come from the country.
7. **Plan mode / scheduling / PDF.** `destination_city` flows into the catalogue, hotel
   record, restaurants, airport transfer and visa lookups. "Arrive in Dubai", "UAE tourist
   visa", "Dubai-itinerary.pdf", "Your Dubai itinerary" use the destination. Dubai-only
   helpers (areas, attractions, airport zones) stay for Dubai; other cities get the generic
   path (meals at the hotel or nearest open restaurant if the supplier has any).
8. **Text.** Prompt persona becomes a GujjuTours trip planner (not Dubai); UI quick starts
   and copy cover several destinations; destination tips fall back to a neutral answer.
9. Supplier money stays AED-based (that is the account, not the destination).

## 2. Admin panel (`feat/admin-panel`)

- **Access:** `ADMIN_EMAILS` (comma separated, case-insensitive). `/auth/me` returns
  `is_admin`. Every admin endpoint checks it server-side; a non-admin gets 404.
- **Data:** migration `009_search_log.sql` adds `search_log` (user, session, message, tool,
  args JSONB, destination, dates, party, result count, error, latency, created_at), filled
  when a turn is saved and backfilled from existing `chat_messages.tool_calls`.
- **API** (`api/admin.py`, router under `/admin-api`): overview (KPIs and daily series:
  active users, sign-ups, turns, searches per service, top destinations, failed searches,
  feedback), users (paged, search, last active, counts), user detail (profile, preferences,
  chats), a chat transcript (messages, cards, tool calls), searches (paged, filters: tool,
  user, destination, errors, date range). Read-only.
- **Web** (`/admin`, `web/src/app/admin/...`): Overview with KPI tiles and simple charts,
  Users table with search, User detail with chats, read-only transcript, Searches table with
  filters. Same design system; "Admin" link in the sidebar only for admins. Proxy rule for
  `/admin-api/*`.
- Admin views of transcripts are logged (who viewed which chat, when).

## 3. OpenTelemetry (`feat/otel-observability`)

- **Python (chat API, agent, supplier client):** `observability.py` sets up traces, metrics
  and logs with OTLP export when `OTEL_EXPORTER_OTLP_ENDPOINT` is set (standard OTEL_* env
  vars; service name `gujjutours-chat-api`). Auto-instrument FastAPI, requests/httpx and
  psycopg; bridge Python logging to OTLP logs.
- **Custom spans:** one per chat turn (session, mode, latency, tools used), one per tool call
  (tool, result count, error), one per supplier call (endpoint, status, latency), one per LLM
  call (model, provider, tokens when returned). Metrics: turn latency, tool calls and
  failures, supplier errors per endpoint. No message text, tokens or secrets in telemetry
  unless `OTEL_CAPTURE_CONTENT=true`.
- **Web:** `instrumentation.ts` (Next.js) exporting server traces over OTLP and passing
  `traceparent` to the API so a turn is one trace end to end.
- `docs/OBSERVABILITY.md`: env setup for Grafana Cloud, Honeycomb or a self-hosted collector.
